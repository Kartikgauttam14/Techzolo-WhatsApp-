# Company WhatsApp integration

The SaaS now implements the Meta Cloud API connection, sending and receiving path. Real delivery still requires Meta credentials, an authorized company number and a publicly reachable HTTPS webhook. Automated tests use synthetic provider responses and signed synthetic events; they do not send messages to real recipients.

## Server configuration

```powershell
npm run setup:whatsapp
```

This generates a unique verification token and AES encryption key in the ignored `.env`, preserving nonempty settings. It prints no secrets. Add these values privately:

| Variable | Purpose |
| --- | --- |
| `META_APP_ID` | Dedicated product app ID above |
| `META_APP_SECRET` | App settings → Basic → App secret; server only |
| `META_GRAPH_VERSION` | Version pinned to `v25.0`; change deliberately after testing |
| `META_LOGIN_CONFIG_ID` | Facebook Login for Business configuration for WhatsApp Embedded Signup |
| `META_WEBHOOK_VERIFY_TOKEN` | Unique secret used by Meta to verify the callback; generated by setup |
| `WHATSAPP_ENCRYPTION_KEY` | Stable 32-byte base64 AES key; generated by setup; back up securely |
| `META_ALLOW_MANUAL_CONNECT` | `true` only for developer/test-number setup; turn off for customer onboarding |
| `APP_URL` | Public application origin, HTTPS in production |

Restart `npm start` after editing `.env`. Never regenerate the encryption key for an existing deployment without a migration: saved tenant credentials and registration PINs depend on it. No API exposes the encryption key, application secret or saved access tokens.

## Meta setup and public callback

Install Cloudflare's official Windows tunnel binary, then start the local relay and quick tunnel in separate terminals:

```powershell
./scripts/install-webhook-tunnel.ps1
npm run webhook:relay
npm run tunnel:whatsapp
```

Copy the `https://....trycloudflare.com` address printed by cloudflared into `META_WEBHOOK_URL` in `.env` with `/api/whatsapp/webhook` appended, restart `npm start`, and register the temporary callback and `messages` field through Meta's app subscriptions API:

```powershell
npm run configure:whatsapp-webhook
npm run check:whatsapp-tunnel
```

The tunnel relay exposes only `GET`/`POST /api/whatsapp/webhook`; CRM and account routes return 404. The check verifies Meta's challenge, route isolation and rejection of unsigned POSTs. The trycloudflare URL changes each time the tunnel is restarted. Update `META_WEBHOOK_URL` in the ignored `.env`, restart the app, and rerun the configuration command after a restart. For production, use a stable HTTPS callback at `https://YOUR_PUBLIC_HOST/api/whatsapp/webhook` and keep the verify token private.

Meta POST events are authenticated using `X-Hub-Signature-256` over the exact raw request bytes with `META_APP_SECRET`. This route deliberately precedes JSON parsing and SaaS session/CSRF middleware. For production, complete Tech Provider onboarding, Meta App Review/advanced access for `whatsapp_business_messaging` and `whatsapp_business_management`, business requirements and app publication. Configure allowed domains, login settings, final legal URLs and data-deletion information using the actual public deployment. Create a Facebook Login for Business configuration for WhatsApp Embedded Signup, use a business integration/system-user token configuration with both WhatsApp permissions, and set its ID as `META_LOGIN_CONFIG_ID`.

An ordinary localhost URL is unreachable from Meta. A temporary webhook-only tunnel may be used with explicit operator authorization for development; do not mistake it for durable production hosting or an approved customer onboarding domain.

## How each company connects

The company owner opens **Integrations → Connect with Meta**. Meta's hosted consent/onboarding flow selects that company's business account and number. The browser submits the returned short-lived code, account ID, phone ID and a session-bound one-time nonce to the backend.

The server exchanges the code, verifies token validity, app ID, expiry, required scopes and phone membership, subscribes the app to the account's webhooks and stores the access token encrypted with AES-256-GCM. A registration PIN is never generated by the server. Developer connections may supply the business's own six-digit phone registration PIN when Meta requires number registration; the PIN is stored encrypted. Only after Meta confirms the requested connection steps is the company marked connected.

For an app administrator/developer's already-registered test number, enable developer connection and supply the WABA ID, phone ID and access token from **this same Meta app**. A registration PIN is optional for an already registered number. Tokens from another app or business account are rejected. App-role/test-recipient restrictions still apply while the app is unpublished.

This version uses the standard Cloud API onboarding flow. It does not implement WhatsApp Business App coexistence/history migration or moving an established workspace to a different WABA. One WABA/number belongs to one SaaS company; disconnecting does not allow another tenant to claim its historical assignment.

## Messages and customer permission

- Signed inbound text, interactive replies and other message types appear in the live inbox. Incoming attachment metadata is retained; authorized users can download attachments through the server, up to 16 MB.
- Inbound routing requires **both** the WABA ID and phone-number ID to match the connected tenant. Unknown or disconnected accounts do not receive new records.
- The service window is 24 hours from the customer's **provider timestamp**, not from when an old webhook was delivered.
- Owners, admins and agents can send real text replies during that window. Viewers cannot send.
- Approved body-text templates can be synchronized from Meta and sent with ordered text parameters. Marketing templates always require verified permission; other business-initiated templates outside the service window require it too.
- Media headers, template buttons/carousels, outgoing attachments, bulk campaign workers and AI/automation execution are not included in this increment. Ordinary CRM campaign/template drafts remain separate from approved live templates.
- A website signup generates a company/phone-bound expiring challenge. The customer opens the returned `wa.me` link and sends `SUBSCRIBE <challenge>` from the entered WhatsApp number. Only a matching signed inbound message records permission and its evidence.
- Incoming STOP/UNSUBSCRIBE/CANCEL/END/QUIT immediately suppress business-initiated messages. Workspace unsubscribe changes also revoke normalized WhatsApp permission.

The UI shows “Accepted by Meta” after the send response; delivered/read status comes only from signed receipts. Idempotency keys prevent double clicks from sending twice. Network timeouts produce an **unknown** outcome; identical unresolved messages are not blindly retried, including after a page reload. The `biz_opaque_callback_data` field correlates a receipt that arrives before an HTTP response or after an uncertain send.

## Storage and operational behavior

`wa_connections`, `wa_registration`, `wa_oauth`, `wa_conversations`, `wa_messages`, `wa_templates`, `wa_optin`, `wa_consent`, `wa_receipts` and `wa_app` are separate SQLite tables. Live messages and Meta approvals cannot be forged by replacing the old CRM workspace JSON. Inbound messages can add a CRM contact if its plan quota has capacity; message history is preserved even when the contact quota is full or the SaaS plan expires. New sends require an active trial/subscription.

The current inbox displays the latest 100 conversations and 100 messages per thread and polls every five seconds while visible. Attachment retrieval requires tenant authentication and restricts the provider download host; it never returns access tokens or upstream download URLs to a client. Disconnect stops future local sends/ingestion and clears the token, preserves historical data and attempts remote app unsubscription. A send already in flight may still complete. If remote unsubscription fails, remove the integration in Meta Business Integrations as well.

Do not run multiple application instances against the same network-mounted SQLite file. Production needs durable storage, backups, monitoring and a retention policy for messages/receipts/consent evidence. This single-process implementation does not include a distributed message worker or automatic outbound retries.

## API surface

Private endpoints require the normal SaaS session and workspace header. Mutations also require CSRF verification.

| Endpoint | Access | Purpose |
| --- | --- | --- |
| `GET /api/whatsapp` | Member | Safe configuration/connection status |
| `POST /api/whatsapp/onboarding` | Owner | Session-bound Embedded Signup attempt |
| `POST /api/whatsapp/complete` | Owner | Exchange code, validate/register/subscribe and connect |
| `POST /api/whatsapp/connect` | Owner, developer mode | Validate an existing developer token |
| `DELETE /api/whatsapp/connection` | Owner | Disconnect company account |
| `POST /api/whatsapp/templates/sync` | Owner/admin | Synchronize Meta template approval data |
| `GET /api/whatsapp/templates` | Member | Company templates |
| `GET /api/whatsapp/conversations` | Member | Company live inbox |
| `GET /api/whatsapp/messages?phone=...&before=...` | Member | Scoped thread messages |
| `POST /api/whatsapp/messages` | Owner/admin/agent | Text or approved body-template send |
| `GET /api/whatsapp/media/:messageId` | Member | Scoped incoming attachment download |
| `GET/POST /api/whatsapp/webhook` | Verify token / Meta signature | Public Meta callbacks |

## Verification

Run `npm test` and `npm run test:e2e`. WhatsApp API tests cover encrypted token storage, app/scope/account validation, uniqueness, signature forgery, unicode/raw bytes, routing, duplicate events, service windows, duplicate sends/timeouts, early receipts, template ownership, signed permission, STOP, expired plans, disconnects and attachment isolation. Two additional browser scenarios exercise the actual UI with a test-only provider transport.

Live acceptance is separate: connect an authorized Meta test number, configure the real HTTPS callback and recipient allowlist, send an inbound customer message, reply through the live inbox, verify delivery/read receipts, confirm a subscriber, test STOP and repeat with a second authorized company after Meta approves third-party access. No real recipient test is claimed until those steps are observed.
